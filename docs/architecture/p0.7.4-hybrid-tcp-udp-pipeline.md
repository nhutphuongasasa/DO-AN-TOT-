# P0.7.4 — Hybrid TCP + UDP / QUIC pipeline

## Scope

P0.7.4 connects UDP protocol analysis and QUIC v1 Initial inspection to the
same `PacketProcessor` already used by live NIC capture and PCAP replay. It
retains the existing TCP reassembly/SNI path and DNS cache path.

## Runtime order

1. Normalize raw IPv4/IPv6 TCP or UDP packet into `PacketRecord`.
2. Apply the selected LAN subnet filter.
3. Parse DNS evidence from the original packet and update the client-scoped DNS cache.
4. Expire idle UDP pseudo-Flows; track the packet in the canonical shared
   `FlowTracker` so TCP and UDP use one session-scoped Flow ID namespace.
5. TCP packets go through the existing TCP reassembly → TLS ClientHello → SNI path.
6. UDP packets go through structural protocol identification. DNS, DHCPv4,
   NTP and STUN remain transport-protocol labels; they are not AppIDs.
7. Only a structurally recognized QUIC v1 Initial candidate enters QUIC parsing:
   header → Initial key derivation → header protection → packet number → AEAD
   authentication → frames → CRYPTO reassembly → TLS ClientHello/SNI.
8. Authenticated SNI is mapped through the same `config/dns_mapping.yaml` rules
   as TCP SNI. Unmapped hostnames remain unresolved; they are not `other-web`.

## Flow and QUIC Connection identity

- A `FlowState` is a transport-level bidirectional 5-tuple. TCP and UDP share
  the canonical `FlowTracker`; UDP idle expiry is separate from TCP lifecycle.
- A `QUICConnectionState` is separate from a UDP Flow and can reference more
  than one UDP Flow ID.
- The tracker indexes DCID/SCID only after an Initial packet authenticates.
  The original DCID remains the Initial key-schedule input.
- The current implementation can link authenticated Initial packets observed
  on another UDP tuple when the destination CID is already indexed. It does
  not decrypt 1-RTT NEW_CONNECTION_ID frames, so it does not claim complete
  general-purpose QUIC migration tracking.
- QUIC connections have a configurable-in-code idle timeout, maximum active
  connection count and maximum CRYPTO bytes. UDP Flows have an independent
  idle timeout and active-flow capacity. Capacity eviction is counted.

## Evidence and protocol labels

- Evidence source `quic_tls_sni` means a hostname was extracted from an
  authenticated QUIC v1 Initial ClientHello.
- A QUIC SNI-only AppID uses the common SNI method with metadata
  `sni_source=quic_tls_sni`.
- DNS is evaluated first; a DNS match is authoritative and ends AppID processing.
- QUIC SNI is evaluated only for UDP Flows unresolved by DNS. A verified QUIC
  SNI match then ends AppID processing for that Flow.
- `FlowState.application_protocol` is `QUIC_INITIAL` when an Initial is
  successfully decrypted. This is deliberately not `HTTP/3` or `h3`: Initial
  inspection alone does not prove that an HTTP/3 request completed.
- `FlowState.quic_connection_id` links the UDP Flow to the QUIC connection.
- ECH is reported as detected; the encrypted inner hostname is not recovered.

## Controls and bounds

`PacketProcessor` constructor controls:

- `enable_udp_analysis` (default `True`): enables UDP protocol/QUIC analysis;
  disabling it does not disable UDP packet Flow tracking or DNS parsing.
- `enable_quic_analysis` (default `True`): disables QUIC decryption while
  retaining UDP protocol identification and UDP Flow tracking.
- `udp_idle_timeout` (default 60 seconds).
- `max_active_udp_flows` (default 10,000).

`UDPAnalyzer` / `QUICConnectionTracker` controls:

- `max_connections` (default 4,096).
- `idle_timeout` (default 120 seconds).
- `max_crypto_bytes` (default 1 MiB per QUIC connection).
- `max_cids_per_connection` (default 8).

## Explicit limitations

- QUIC v1 Initial only. No QUIC v2, Retry validation, 0-RTT, 1-RTT or HTTP/3
  frame/request decoding.
- No ECH inner-SNI recovery.
- CID linkage is based on CIDs seen in authenticated Initial packets only;
  no NEW_CONNECTION_ID frame tracking or full migration guarantee.
- QUIC Initial decrypt success and SNI recognition are separate from successful
  application HTTP/3 requests.
- Live NIC and PCAP parity use the same processor code, but this build-container
  validation does not replace a fresh user-laptop live capture acceptance.
