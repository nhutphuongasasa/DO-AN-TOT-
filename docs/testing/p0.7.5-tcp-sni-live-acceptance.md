# P0.7.5 — TCP SNI live acceptance

## Purpose

Verify the TCP path independently of QUIC. The probe client explicitly uses
HTTP/1.1 (`curl --http1.1`) and bypasses configured HTTP proxies
(`--noproxy '*'`) so that the target TLS ClientHello is expected to be visible
on the selected local interface. This test does not use the HTTP/3 generator.

## Target applications

| Application | Probe hostname |
|---|---|
| ChatGPT | `chatgpt.com` |
| Facebook | `www.facebook.com` |
| TikTok | `www.tiktok.com` |
| YouTube | `www.youtube.com` |
| Spotify | `open.spotify.com` |

## Run on Linux laptop

From the extracted project directory, run:

```bash
./setup_linux.sh
sudo ./run_tcp_appid_test.sh wlp62s0
```

Optional PCAP path:

```bash
sudo ./run_tcp_appid_test.sh wlp62s0 p075-tcp-five-apps.pcap
```

The script uses `dumpcap` rather than `tcpdump` for this capture workflow.
On the tested Ubuntu setup, AppArmor denied signal delivery to the confined
`tcpdump` process launched from the VS Code terminal. `dumpcap` accepted
SIGINT and exited cleanly. P0.7.5.3 writes the in-progress capture to a unique
private directory under `/tmp`, sends SIGINT after the probes, waits for
`dumpcap`, validates the non-empty file, and only then moves it into the
project/output path with mode `0644`. The hard capture limit is 180 seconds by
default. Override it when needed with, for example,
`sudo CAPTURE_MAX_SECONDS=240 ./run_tcp_appid_test.sh wlp62s0`.

The script:

1. Detects the IPv4 subnet configured on the selected interface.
2. Captures `tcp port 443` with `dumpcap` into a unique `/tmp/p075-tcp-capture-*` temporary directory while it sends five HTTP/1.1 HTTPS requests; capture is bounded by `CAPTURE_MAX_SECONDS` (default 180 seconds).
3. Writes a per-target HTTP result report (`*-traffic-report.tsv`).
4. If `tshark` is installed, lists unique TCP TLS SNI observations.
5. Replays the exact PCAP through `appid.capture.pcap`, which constructs the
   same `PacketProcessor` used by live capture and prints per-flow AppID,
   identification method and reason code.

The script must be run with `sudo` because it needs capture privileges. It uses `dumpcap`; do not replace it with background `tcpdump` in this workflow on systems where AppArmor denies signals to the tcpdump profile. The temporary PCAP is not published to the requested output path until `dumpcap` has exited and the capture is confirmed non-empty. On success, the final PCAP is mode `0644`. On errors or Ctrl+C, cleanup stops and waits for `dumpcap` and removes the temporary capture directory. It deliberately bypasses proxies; if the network policy requires a proxy, this direct test may fail to connect and should be recorded as an inconclusive network probe, not a TCP SNI parser failure.

## Acceptance criteria

- The capture file is non-empty and contains TCP/443 packets.
- The SNI observations include the expected target hostnames. A successful
  HTTP request alone does not satisfy this condition.
- PacketProcessor PCAP replay reports the expected application IDs on TCP
  flows with `method=sni` (or `hybrid_dns_sni` when matching DNS evidence is
  present).
- A hostname outside configured application rules remains unclassified; it
  must not be forced into `other-web`.
- Record HTTP probe results, SNI observations, replay counters and the exact
  command/interface used. Mark any target with no visible ClientHello as
  INCONCLUSIVE for that target.

## User laptop evidence — 2026-11-24

The user ran `sudo ./run_tcp_appid_test.sh wlp62s0`. All five forced HTTP/1.1
probes completed with HTTP 200 and `curl_exit=0`:

- `chatgpt.com`
- `www.facebook.com`
- `www.tiktok.com`
- `www.youtube.com`
- `open.spotify.com`

`tshark` independently observed all five expected hostnames in TCP TLS
ClientHello records. It also observed unrelated background hostnames; these
must not be counted as target-app results.

The first PacketProcessor replay reported `raw=5669 parsed=0
tracked=0 unsupported=5669`. Scapy warned `unknown LL type [1] ... Using Raw
packets`. This was traced to constructing `PcapReader` before importing
`scapy.all`, so Scapy's Ethernet link-layer decoder registry had not been
initialized. The replay loader now imports `Ether` from `scapy.all` before
constructing `PcapReader`.

The first script run also waited indefinitely while stopping background
`tcpdump`. Follow-up kernel audit records established the cause: AppArmor
denied SIGTERM to the `tcpdump` profile (`operation="signal"`,
`denied_mask="receive"`, `peer="vscode"`). A test with `tcpdump -Z root`
was denied as well. In contrast, `dumpcap` ran with label `vscode (unconfined)`,
accepted SIGINT, exited with status 0 and wrote a readable PCAP. P0.7.5.2
therefore changes the runner to `dumpcap`, uses SIGINT for normal shutdown and
sets a 180-second hard capture duration as a fallback.

**Acceptance status: PARTIAL, with user-laptop PacketProcessor evidence.** On
2026-11-24 the user replayed the valid 3.5 MB TCP PCAP: `raw=4054`,
`parsed=4054`, `tracked=4054`, `unsupported=0`, `parse_errors=0`. The five target
flows were classified as `chatgpt`, `facebook`, `tiktok`, `youtube` and
`spotify`, all with `method=sni` and `reason=SNI_HOSTNAME_RULE_MATCH`. The
replay also reported 104 unrelated/unmapped SNI observations and 8 SNI errors;
these are not target-app matches. The prior capture runner still hung during
cleanup, so P0.7.5.2 live-run acceptance must be repeated with the new
`dumpcap` runner before marking the script correction verified end-to-end.

## P0.7.5.3 corrective update

P0.7.5.2 had two packaging/runner defects:

1. Several shell entrypoints were archived without execute permission; in particular, `run_tests.sh` had mode `0600`, so `./run_tests.sh` failed with permission denied.
2. The live runner wrote the in-progress PCAP directly to its final project path while `dumpcap` was still running. This exposed a partial output file and did not satisfy the required temporary-capture lifecycle.

P0.7.5.3 fixes both issues. All project `.sh` files are packaged with mode `0755`. `run_tcp_appid_test.sh` creates a unique temporary directory under `/tmp`, records the capture there, sends SIGINT to `dumpcap`, waits for its exit, checks that the temporary PCAP exists and is non-empty, and only then moves it to the requested project/output path and applies mode `0644`. EXIT/INT/TERM cleanup stops and waits for an active capture process and removes temporary artifacts. The default hard capture duration remains 180 seconds.


Accept the capture stage only when the runner reports a non-empty final PCAP with mode `644`, the file is readable by `tshark` (when installed), and PacketProcessor replay completes with parsed packets and the expected TCP AppIDs. For this five-host probe, verify the expected SNI names and corresponding `chatgpt`, `facebook`, `tiktok`, `youtube`, and `spotify` flow classifications; HTTP 200 responses alone are insufficient. A capture/replay is not accepted merely because the file exists.

## P0.7.5.4 — strict automated acceptance gate

The P0.7.5.3 live run on the user's Ubuntu laptop produced a valid 3,654,764-byte
PCAP with 2,541 captured packets and zero reported drops. `tshark` observed all
five target SNI names, and PacketProcessor replay reported 2,541 raw/parsed/
tracked packets, zero unsupported packets, zero packet parse errors, and five
identified target flows. The run also reported one SNI parser error; this is
reported diagnostically and is not treated as a packet-decoding failure.

P0.7.5.4 makes the acceptance command fail closed instead of merely printing a
replay summary:

- A missing, zero-length, or header-only PCAP is rejected before replay.
- The generated TSV must contain all five expected probe rows, matching hostnames,
  `curl_exit=0`, and a valid HTTP status. HTTP status is transport-probe evidence
  only; it does not establish AppID.
- PacketProcessor must parse and track packets, with no unsupported packets or
  packet-level parse errors.
- Every target app must have at least one TCP Flow classified by `sni` or
  `hybrid_dns_sni`, with the exact expected hostname present in `tls_sni` evidence.
- Missing any one target app produces a non-zero exit code and names the missing
  app. `sni_parse_errors` remains visible as a diagnostic counter because
  unrelated/background ClientHello records may fail independently of the five
  target flows; it does not silently invalidate otherwise complete target evidence.

Run the strict acceptance gate with:

```bash
sudo ./run_tcp_appid_test.sh wlp62s0
```

The runner invokes `scripts/verify_tcp_appid_acceptance.py` after dumpcap has
stopped, the PCAP has been validated/moved, and the traffic report is available.
A final `[PASS] Traffic report, PCAP replay, and all five TCP/SNI AppIDs verified.`
line is the acceptance success condition. The strict verifier is also covered by
unit tests for complete success, a missing target, wrong transport/method, and
failed traffic probes.

The earlier P0.7.5.3 laptop output is evidence that the current PCAP and replay
path did identify all five apps. The new strict P0.7.5.4 gate itself still needs
to be run once on the laptop after installing this package; no new live run is
claimed by the packaging environment.
